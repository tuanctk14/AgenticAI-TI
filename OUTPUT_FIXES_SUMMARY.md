## Issue 1: LLM Hallucination in agent_matcher

### Problem
Agent_matcher first iteration was allowing LLM to:
- Generate fake device IPs (e.g., 192.168.1.100 when no match)
- Output ANSWER with generic remediation alongside tool call
- Mix reasoning output with deterministic tool call

### Root Cause
LLM given open-ended instruction to "output comprehensive analysis" even before tool execution.

### Solution
Hardcoded agent_matcher first iteration in `call_agent()`:
```python
if agent_name == "agent_matcher" and state.get("last_agent") != "agent_matcher":
    if cves:
        response = "ACTION: match_cves_with_cmdb\nARGUMENTS: {}"
        # ... [deterministic tool call only, no LLM reasoning]
```

### Result
- ✅ First iteration deterministically calls matching tool
- ✅ No fabricated device data
- ✅ Second iteration uses `_build_full_analyst_output()` for comprehensive output

## Issue 2: Output Duplication

### Problem
`_print_summary()` was printing the entire CVE analysis result again after agent_matcher already output it.
- Same CVE details printed twice
- Same MITRE/NIST sections printed twice  
- Result shown 3 times total (from agent + _print_summary + report sections)

### Solution
Updated `_print_summary()` in `main.py`:
```python
def _print_summary(result: dict):
    last_response = result.get("last_agent_response", "")
    
    # Nếu agent_matcher đã output đầy đủ → chỉ in metadata
    if "KẾT QUẢ QUÉT LỖ HỔNG" in last_response or "THIẾT BỊ BỊ ẢNH HƯỞNG" in last_response:
        print("\n" + "="*70)
        history = result.get("agent_history", [])
        print(f" Agents: {' → '.join(history)} | Bước: {result.get('num_steps', 0)}")
        print("="*70)
        return  # Skip detailed output
    
    # Other workflows (IOC, device-only) keep original behavior
```

### Result
- ✅ Comprehensive analysis printed once (by agent_matcher)
- ✅ Summary metadata printed once (agents flow, step count)
- ✅ No duplication for analyst-first CVE queries
- ✅ Other workflows unaffected

## Issue 3: Remediation Specificity

### Problem
Remediation section was supposed to have per-technique and per-control actions, but:
- Was generated by agent_matcher LLM (prone to hallucination)
- Often defaulted to generic advice
- Lacked technical depth

### Solution
Implemented code-based remediation in `_build_full_analyst_output()`:

1. **Created fallback tables** (lines 504-519):
```python
FALLBACK_TECHNIQUE_ACTIONS = {
    "T1190": ["Monitor web application logs", "Implement WAF rules", "Patch immediately"],
    "T1059": ["Restrict command execution", "Monitor processes", "Disable scripts"],
    "T1071": ["Monitor network traffic", "Implement segmentation", "Identify C2"],
    # ... etc
}

FALLBACK_CONTROL_ACTIONS = {
    "SI-2": ["Apply latest patches", "Maintain inventory", "Test patches"],
    "SI-3": ["Deploy malware protection", "Keep definitions current", "Monitor"],
    # ... etc
}
```

2. **Added Remediation Section** to output (lines 667-716):
```python
# Per-technique remediation (if techniques exist)
for tech in techniques:
    lines.append(f"  {tech_id} - {tech_name}:")
    actions = FALLBACK_TECHNIQUE_ACTIONS.get(tech_id, [...])
    for i, action in enumerate(actions, 1):
        lines.append(f"    {i}. {action}")

# Per-control remediation (if controls exist)
for ctrl in controls:
    lines.append(f"  {ctrl_id} - {ctrl_title}:")
    actions = FALLBACK_CONTROL_ACTIONS.get(ctrl_id, [...])
    for i, action in enumerate(actions, 1):
        lines.append(f"    {i}. {action}")

# Fallback for when no mapping exists
if not techniques and not controls:
    lines.append("  Hướng khắc phục chung:")
    lines.append("    1. Cập nhật phần mềm...")
```

### Result
- ✅ Remediation always present (never skipped)
- ✅ Specific actions for each MITRE technique
- ✅ Specific controls for each NIST framework item
- ✅ Fallback remediation for unmapped CVEs
- ✅ Actionable, not generic advice

## Issue 4: Generic Patch Line Removal

### Problem
Old system instruction for agent_matcher had:
```
[REMEDIATION]
0. Patch product to latest version
Per technique:
  ...
Per control:
  ...
```

The "BƯỚC 0" generic line was always printed, even when more specific actions were available.

### Solution
Replaced LLM-based remediation generation with code-based approach (Issues 3 & 4 solved together):
- No more "patch to latest version" template line
- Remediation now comes from fallback tables with specific actions
- Structure: Technique actions → Control actions → Fallback if nothing matched

### Result
- ✅ No generic "patch" line ever appears
- ✅ All remediation is specific and technique/control-aligned
- ✅ Analyst-grade guidance always provided

## Bonus: CWE-Based MITRE/NIST Mapping

### Enhancement
When MITRE/NIST tools are called, we now inject CWE IDs to enable fallback mapping:

**In `call_tool()` (lines 443-460)**:
```python
elif tool_name in ["get_mitre_attack_info", "get_nist_controls"]:
    cve_id = args.get("cve_id", "")
    if cve_id:
        # Extract CWE IDs from collected CVEs
        for cve in state.get("collected_cves", []):
            if cve.get("id") == cve_id:
                if cve.get("cwe_ids"):
                    args["cwe_ids"] = cve.get("cwe_ids")
                if cve.get("description"):
                    args["cve_description"] = cve.get("description")
                break
```

### Result
- ✅ MITRE/NIST tools receive CWE context for better mapping
- ✅ Fallback to CWE mapping when direct CVE mapping unavailable
- ✅ Increased mapping coverage for uncommon CVEs
- ✅ Semantic analysis of CVE descriptions enabled
